# 신규 코드 voicing 전수 감사 — 수정 전 원인 보고

이번 작업은 감사만 수행했다. src/App.jsx, chordTheory, additionalChords, Fretboard 및 기존 운지 데이터는 수정하지 않았다.

## 핵심 판정

- Aadd2 1구간 522225를 재현했다. 음은 맞지만 해당 형태의 실전 대표성 근거 없이 G 형태를 이동한 결과다. 대표값 승인 불가/미검증으로 분류한다. 손 크기와 기법에 따라 연주 가능할 수 있다는 것과 일반적인 대표 운지라는 것은 별개다.
- Fadd9는 현재 로컬 소스 및 실제 모바일 렌더링에서 135211, F–C–G–A–C–F였다. 3번줄은 2프렛 A이며, 제보한 135311의 Bb는 재현하지 못했다. 사용자 화면과 다른 이유(빌드·페이지·저장 상태 등)는 확인되지 않았으므로 추정 원인으로 단정하지 않는다.
- 제보한 135311을 메모리상의 감사용 복사본으로 검사하면 Bb(허용되지 않은 음), A(필수음 누락)를 모두 검출한다. Fadd9 실제 데이터는 변경하지 않았다.
- 신규 데이터의 272개 대표 조합 모두 정확한 개별 운지 출처/검수 기록이 없어 대표성 미검증으로 분류했다. 이는 272개가 모두 연주 불가능하다는 뜻이 아니다.

## 기존/신규 경계와 생성 경로

신규 14타입: Major 5/add2/add11/maj11/maj13/11/13/7b5/7#5/7b9/7#9, Minor m11/m13, Dim dim7.
기존 공식에 운지만 추가한 타입: 6/9, m7b5.
기존 운지를 유지하고 표시명만 변경한 타입: minor add9 → m(add9).
Fadd9는 기존 App.jsx의 eadd9/aadd9 템플릿을 그대로 사용한다. 이번 신규 표인 additionalChords.js에 add9는 없다.

생성 흐름은 getChordShapeTemplates → buildChordTemplateCandidates → buildGeneratedChordShapeOption → buildChordReferencePositionMap이다. 신규 데이터는 rootString/상대 fret/손가락 tuple을 직접 작성한 템플릿이며, 이를 12프렛 단위로 이동한다. 코드 음을 지판 전체에 분산하는 fallback이 이번 신규 운지의 실제 원인은 아니다. 다만 템플릿을 직접 썼다는 사실만으로 사전에서 검증된 형태가 되는 것은 아니다.

기존 selector 점수는 maxFret × 10 + span × 2 + priority다. 최종 구간은 시작 fret, 최대 fret, 원본/생성 우선순위, 템플릿 우선순위, ID 순이다. 여기에 대표 기타 사전의 순위, 실제 연주 검수, 출처 확인 단계가 없다.

## Aadd2 원인

additionalChords.js의 g-add2는 6번줄 루트를 기준으로 상대 fret [0,-3,-3,-3,-3,0], 손가락 [3,1,1,1,1,4]다. A 루트를 6번줄 5프렛에 두면 522225가 된다. 가운데 네 줄은 2프렛 검지 바레, 바깥 두 줄은 5프렛 약지/소지다.

실제 발음: A2–B2–E3–A3–C#4–A4. A–B–C#–E 구성음을 모두 포함한다. 낮은 2도 음역을 강제하려고 넣은 C/G형 두 템플릿 중 G형은 score 56, C형은 base 12/score 126이어서 G형이 먼저다. 개방 C/G 형태를 이동했을 때 발생하는 손가락 부담과 대표성의 변화는 검증하지 않았다.

이전 참고 자료는 [add2/add9의 음역 차이를 설명하는 교육 글](https://www.guitarlessonsbybrian.com/home/is-it-an-add-9-or-add-2-chord/)이다. 이 글은 522225를 대표 Aadd2로 선정하는 근거가 아니다. 이번 조사에서도 그 정확한 형태를 대표 운지로 승인할 근거를 확보하지 못했다.

## 추가로 확인된 이름 해석 결함

1. Dbm7b5/Ebm7b5/Gbm7b5/Abm7b5/Bbm7b5의 직접 getChordMetaFromLabel 경로가 flat 루트와 m7b5를 잘못 읽는다. 신규 파서의 정규식에 m7b5가 빠져 기존의 # 전용 루트 파서로 넘어간다. 5개 이름 × 4후보 = 20행이다. 기존 파서의 한계가 보충 타입의 검증에서 누락된 것으로, 구조화된 root/quality/extension으로 생성하는 지판은 음이 맞으며 모든 UI 경로가 틀린다는 의미는 아니다. 미니반주의 flat 정규화 경로는 이 경우 정상이다.
2. minor add9 표시명을 m(add9)로 바꾼 후 getMiniChordLabelParts가 괄호 안을 통째로 삭제한다. Cmadd9는 minor/add9로 읽지만 Cm(add9)는 minor/none으로 읽는다. 17개 루트 표기 모두 재현했다. 이는 표시명 변경으로 생긴 실제 경계 회귀이며, 기존 운지 snapshot 비교로는 검출되지 않았다.

## 이전 검증 보고의 정정

기존 712개 검사 통과는 구성음 및 일부 손가락/바레 조건의 통과였다. '실제 연주 가능하고 검증된 대표 기타 voicing' 전체를 검증한 것으로 보고한 것은 부정확했다. 이전 검사는 생산 코드의 공식과 pitch 계산 함수에 의존했고, 대표성 출처·실연 검증·미니반주 이름 왕복 경로가 빠져 있었다. 이전 문서의 712개 통과 문구를 대표성 인증으로 해석해서는 안 된다.

기존 204개 정상/보존 대상 조합의 회귀 비교는 이번에도 동일했다(m(add9) 표시 문자열만 정규화). 6/9·m7b5 24개는 이전에 명시한 보충 범위다. 운지가 같다는 결과가 모든 UI·파싱 경로의 정상 동작을 뜻하지는 않는다.
