# 악보 편집·재생 실동작 점검 — 2026-09-18

## 환경과 한계
- 로컬 앱을 실제 Chromium 브라우저에서 조작: 모바일 390×844, 데스크톱 1440×1000.
- 입력 성능: 모바일 크기, CPU 4배 감속, 악기별 8마디, 이동/입력 56개 측정 표본. 입력 핸들러에서 다음 animation frame까지의 앱 계측값이며 물리적 터치 지연을 포함하지 않음.
- 별도 브라우저 프로필에서 테스트용 악보 사용. 사용자 저장 악보는 변경하지 않음.
- 실제 Android/iPhone의 발열, 터치 드라이버, Safari, 오디오 출력 지연은 미검증. 모든 렉이 제거됐다는 의미는 아님.

## 재현하고 수정한 문제
1. 줄 나눔 설정이 없을 때 렌더마다 새 빈 배열이 만들어져 커서 이동에도 줄 배치·간격을 재계산. 고정 빈 배열과 메모이제이션 적용.
2. 커서 위치를 찾기 위해 모든 마디의 Shadow DOM을 검색. 현재 마디만 검색하도록 수정.
3. 재생 중 BPM 변경 시 새 악보 객체로 인식해 정지. 음악 데이터 변경과 BPM/보기 변경을 구분하고 같은 음악적 위치에서 템포 변경.
4. 오선보/TAB 보기 전환이 편집 커서의 재생 위치 이동까지 호출. 보기 전환에서는 재생 위치를 변경하지 않도록 분리.

## CPU 4배 감속 입력 지연
| 악기 | 수정 전 p95 | 수정 후 p95 | 수정 후 중앙값 |
|---|---:|---:|---:|
| 기타 | 211.6ms | 115.5ms | 89.3ms |
| 베이스 | 174.6ms | 112.6ms | 91.0ms |
| 우쿨렐레 | 186.2ms | 111.8ms | 88.3ms |

위 수치는 같은 입력 시나리오의 단일 전후 측정이며 기기 성능에 따라 달라짐. 커서 이동에 따른 악보 재그리기는 전후 모두 0회. 개선 대상은 불필요한 계산과 DOM 검색.

## 확인 결과
| 범위 | 확인 방식·결과 |
|---|---|
| 기타·베이스·우쿨렐레 | 각 악기 입력·상하좌우 이동·저장, 실제 악기 선택 드롭다운 전환 통과 |
| 마디 추가/삭제 | 추가 후 프렛 입력, 음 삭제·재입력, 마디 삭제 후 마디 수 확인 통과 |
| 줄 편집 | 2마디 배치 → 개별 줄 나눔 → 저장 → 재생 통과 |
| 피킹 | 다운/업 교대 실제 적용 및 저장값 확인 통과; 음 길이 불변 단위검사 통과 |
| 빔 | 모바일·데스크톱에서 8분음표 4개 범위 선택·연결·저장, 길이 불변 확인 |
| 주법 | H/P/SL/붙임줄/팜뮤트/비브라토 실제 UI 입력·저장·재로드·재생 통과 |
| 도돌이표 | 시작/끝 직접 지정, 4마디→1마디 실제 진행바 복귀 확인 |
| BPM | 세 악기 재생 중 120→90 변경 후 재생 유지 확인 |
| 보기 전환 | 오선보만/TAB만/둘 다, 재생 유지 및 음악적 진행 위치 증가 확인 |
| 진행바 | 주법 악보 반복 재생 동안 마디별 재그리기 횟수 불변; 진행바 좌표 이동 확인 |
| 점음표·쉼표·셋잇단 | 실제 브라우저 오디오 시계 위치와 진행바 좌표 비교 통과; 반복·일시정지/재개·길이 수정 후 위치 확인 |
| 선택적 악보 소리 | 입력 시 오디오 소스 0, 기본 메트로놈만 재생, 피아노 체크 시 소스 생성, 해제 후 음원 스케줄링 중단·연습 지속 |
| 오류/빌드 | 최종 브라우저 시나리오 pageerror 없음, 관련 단위검사 145/145, 프로덕션 빌드 통과 |

피킹·빔·팜뮤트·비브라토는 음표 길이를 바꾸는 기능이 아니므로 진행바 속도를 임의로 바꾸지 않음. H/P/SL/붙임줄은 기존 길이·연결 규칙을 따르고, 점음표·셋잇단·쉼표·반복 순서는 시간축에 반영됨. 하모닉스·아르페지오와 D.C./D.S./엔딩 등 추가 경로는 이번 관련 단위검사에 포함되었으나 모든 조합을 UI에서 다시 입력하지는 않음.

기존 테스트 2개는 현재의 빈 입력칸 처리 규칙 및 오류 문구와 어긋나 있어 기대값을 정리함. 실제 입력된 음표/쉼표 덮어쓰기 방지 검사는 유지.
