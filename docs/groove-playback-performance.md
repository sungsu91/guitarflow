# 그루브 진행선 및 재생 성능 수정

## 원인과 수정

- 진행선 위 삼각형 의사 요소를 삭제하고 수직선만 유지.
- 독립 메트로놈에서 사용하지 않는 Stage 3 진행 상태를 매 프레임 갱신하던 코드를 제거. 다른 연습 화면의 진행 상태 업데이트는 유지.
- 그루브에서 표시하지 않는 일반 메트로놈 beat state의 매 박 동기 렌더링을 건너뜀. 오토매터·트래커 계산은 기존 audio clock/runtime에서 유지.
- 그루브 데이터는 App 인스턴스가 소유한 store로 공유. 오디오는 ref, 모바일/데스크톱/확대 편집은 useSyncExternalStore로 동일한 snapshot을 읽음. 칸 편집이 앱 전체를 다시 렌더링하지 않음.
- 변하지 않은 트랙 객체를 보존하고 React.memo로 변경된 트랙만 갱신.
- 루트 CSS 변수 및 left 좌표의 매 프레임 변경을 제거. 진행선 transform만 Web Animations API로 합성하며 AudioContext 시간과 12ms 이상 벌어지면 재동기화. BPM·박자·재시작 시 새 오디오 기준으로 애니메이션을 갱신.
- 오디오 스케줄러 간격 25ms / 선예약 180ms 및 음원 타격 시간 계산은 변경하지 않음.

## 측정

로컬 Vite 개발 서버, headless Edge, 390×844 모바일 에뮬레이션, 디스코 펑크 풀 퍼커션 8트랙·112 BPM. 기본 재생은 12초 측정, 편집 조건은 재생 중 동일 칸 12회 토글. CPU 저속 조건은 CDP 4배 감속. 아래 프레임 간격은 메인 스레드 requestAnimationFrame 콜백 간격으로, 실제 기기의 디스플레이/스피커 출력 지연을 측정한 값이 아님.

| 조건 | RAF p95 | RAF p99 | 최대 RAF 간격 | 늦은 음원 예약 | 누락된 16분음표 시점 |
|---|---:|---:|---:|---:|---:|
| 수정 전 기본 재생 | 97.4ms | 153ms | 173.8ms | 0 | 0 |
| 전체 화면 매 프레임 갱신 제거 후 | 7ms | 7.1ms | 7.3ms | 0 | 0 |
| 수정 중 CPU 4배 저속 + 편집 (앱 상태 변경 잔존) | 7.1ms | 222.2ms | 402.8ms | 0 | 13 |
| 최종 CPU 4배 저속 + 편집 | 7ms | 13.8ms | 34.8ms | 0 | 0 |

최종 편집 측정에서 최소 선예약 여유는 약 143.7ms이며 오디오 예약 간격 오차는 1.6e-15초 미만(부동소수점 오차 수준). 50ms 이상 long task는 0회. 34ms를 조금 넘는 메인 스레드 프레임은 5회 남아 있었으며, 이를 숨기거나 모든 기기에서 무조건 무지연이라고 판단하지 않음. 진행선은 main-thread RAF마다 직접 이동시키는 대신 합성 가능한 transform 애니메이션으로 계속 움직임.

## 회귀 확인

- 메트로놈·그루브·데스크톱 레이아웃 Node 테스트 45개 통과, 프로덕션 빌드 통과.
- 360/390/430px에서 패턴·BPM 전환, 8트랙, 음소거·볼륨·강약, 확대 편집 공유 및 저장 재검증.
- scripts/verify-groove-performance.mjs는 늦은 예약·누락·오디오 격자 오차 및 지속적인 RAF 지연을 검사.

측정은 이 개발 환경에 한정됨. 브라우저 백그라운드 제한, 기기 과부하, 실제 모바일 하드웨어의 오디오 출력 지연까지 무조건 보장하는 결과는 아님.
