# 악보 재생 진행선 지연 수정 — 2026-10-03

## 재현과 원인

사용자가 가져온 81마디 악보의 38마디부터 BPM 110, 오선보+TAB 표시로 재현했다. 격리된 Chrome 프로필을 사용했으며 사용자 브라우저의 저장 악보는 수정하지 않았다.

- 수정 전: 마디 전환마다 약 354–392ms의 긴 작업, 시작 시 약 787ms. 악보 SVG 자체가 다시 생성되는 현상은 없었다.
- 개별 DOM 변경을 측정한 결과, 재생 마디 `select.value` 변경은 약 404ms, 진행선의 SVG 재부착은 약 440ms였다. 선택된 option의 글자만 변경하면 약 0.6ms였다.
- 트레이스에서 전역 `:has()` 스타일 무효화로 약 23,000개 요소를 재계산했다. 진행선의 인라인 `style.visibility` 변경도 같은 문제를 유발했다.

## 변경

- `PlaybackBarSelect`: 재생 중 선택된 option은 유지하고 현재 마디의 글자만 갱신한다. 사용자가 메뉴를 조작할 때 실제 마디 선택으로 전환한다. 마우스/터치 선택 후에는 현재 마디 표시로 복귀하며, 키보드 화살표 탐색도 유지한다.
- `scorePlayheadLayer`: 악보를 그릴 때 페이지마다 진행선을 준비한다. 재생·정지·페이지 전환 중에는 노드를 추가하거나 옮기지 않고 SVG visibility 속성으로 표시한다.
- 마디 선택 영역은 재생 시작/종료 때 다시 만들지 않는다. 강조 속성은 실제로 바뀌는 마디만 수정한다.
- 데스크톱/모바일의 화면 구성은 유지하고 공통 재생 표시 로직을 수정했다. 음높이, 리듬, 원본 데이터와 오디오 타임라인은 변경하지 않았다.

## 검증

- 전체 자동 테스트 **1,754개 통과**, 프로덕션 빌드 성공.
- 긴 악보의 페이지/반복 이동, 일시정지 후 재개, 마디 선택의 화살표·마우스 동작, 정지 후 진행선 숨김을 검사했다.
- 실제 기타 출력 PCM을 측정했다. 클릭음과 카운트인은 꺼서 악보 소리만 검증했다.
- 일반 개발 화면: 재생 중 최대 프레임 간격 데스크톱 13.9ms, 모바일 화면 27.8ms. 재생 중 악보 노드 추가 0건.
- 배포 빌드/데스크톱 두 페이지: 최대 11.3ms, 50ms 초과 0건. 원본 저장 데이터 변화 없음.
- 배포 빌드/모바일 화면: 최대 16.4ms, 50ms 초과 0건, 10→11페이지 이동 확인.
- 다른 악보: 내장 `G-scale-rhythm-bridge`의 리듬으로 구성한 64마디 악보에서 최대 10.5ms, 50ms 초과 0건. 특정 곡이나 마디 번호에 의존하지 않는다.
- 사용자의 화면처럼 자동 스크롤을 중단한 상태에서도 최대 13.6ms, 50ms 초과 0건. 현재 위치 버튼을 유지한 채 진행선이 이동한다.
- 배포 빌드/CPU 4배 감속: 95백분위 27.9ms, 최대 90.2ms. 마디마다 발생하던 0.4초 정지는 재현되지 않았다.

수치는 이 컴퓨터의 격리 Chrome에서 측정한 값이다. 모바일은 440×956 화면 조건이며 실제 휴대폰 기기 테스트는 아니다. 개발 빌드의 CPU 4배 감속에서는 React 개발 모드 비용으로 최대 281ms가 남았으므로 배포 빌드 결과와 구분한다.

재생 시작 직후의 UI/음원 준비 비용은 별도로 남아 있다(배포 일반 약 0.4초, CPU 4배 감속 약 3.8초). 위 프레임 통계는 재생 시작 마디 이후의 연속 이동 구간이다. 이번 수정은 OCR 인식 정확도나 36·41마디의 리듬 경고를 수정한 것이 아니다.
