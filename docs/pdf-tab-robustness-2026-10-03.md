# PDF TAB 자체 오류 탐지와 인식 보완

검증일: 2026-10-03. 앱의 악보 렌더러와 독립된 ReportLab 도형/글꼴로 정답이 알려진 TAB을 만들고, 실제 PDF.js + Worker + 로컬 Tesseract 경로로 분석했다. 정답/파일 이름에 따른 분기는 인식 코드에 추가하지 않았다. 기능과 데이터는 공유 계층에서 변경했고 모바일·데스크톱 편집 화면은 변경하지 않았다.

## 테스트 범위

- Helvetica, Times-Roman, Courier, Helvetica-Bold 네 글꼴.
- 글꼴마다 원본 텍스트 PDF, 200/110/75dpi 이미지 PDF, 흐림, 점 잡음의 여섯 조건.
- 별도 음 배열을 사용한 흐린 리듬, 위쪽 줄기 두 조건을 더해 총 26개 PDF / 104마디 / 운지·뮤트 1,014개.
- 4분·8분·16분음표와 혼합 리듬, 여섯 현, 두 자리 프렛, X 뮤트, 동시음. 제목의 숫자는 인식 대상에서 제외되어야 한다.
- 매 파일은 새 브라우저 페이지에서 무작위 UUID 파일 이름으로 입력한다. 파일 간 OCR 캐시는 공유하지 않는다. 정답은 Node의 채점기에만 전달한다.
- 음표 열의 순서가 바뀌거나 빠진 경우를 숨기지 않도록 원본 페이지의 위치로 대조한다. 확대 마디는 그 마디에 기록된 원본 좌표 크기를 사용한다.

이는 다양한 실전 악보를 무작위 추출한 정확도 평가가 아니다. 같은 짧은 음 배열의 글꼴/화질 변형이 포함된 재현 가능한 스트레스 테스트다. 손글씨, 기울어진 촬영, 복잡한 주법, 모든 쉼표/셋잇단 표기는 이번 합성 코퍼스에 포함하지 않았다. 기존 실제 악보와 기존 회귀 검사는 별도로 실행했다.

## 발견하고 수정한 오류

1. 좁은 글꼴의 `11`을 두 개의 `1`로 나누는 문제: 동일한 리듬 줄기 주변에 놓인 두 조각에 한해서 넓은 글자 간격을 허용한다. 별도 줄기가 있는 인접 음과 서로 다른 현은 합치지 않는다.
2. 가는 앞자리 `1`이 너무 일찍 제거되어 `10`이 `0`으로 입력되는 문제: 조각을 묶기 전에는 가는 숫자를 보존하고, 묶은 뒤 줄기 조각을 제외한다. 숫자 사각형을 합칠 때 위쪽으로 치우친 글자의 높이도 보존한다.
3. 네이티브 Courier의 두 자리 숫자 누락: PDF 텍스트의 글꼴·위치 검사를 통과한 글자에 이미지의 잉크 폭 제한을 중복 적용하지 않는다. 이미지 OCR의 폭·문자 수 검사는 유지한다.
4. 흐린 빔이 4분음표로 바뀌는 문제: 줄기 주변에 어두운 가로 획이 전혀 없을 때만 일반 잉크 마스크에서 연결된 빔을 다시 읽는다. 밝은 잡음은 깃발로 인정하지 않는다. 원본에 잉크가 남아 있는 단일 픽셀의 가로 끊김만 연결하며 흰 여백은 연결하지 않는다.
5. 저해상도에서 TAB 한 줄 전체가 누락되는 문제: 선 간격 중앙값이 한쪽으로 치우쳤을 때 인접 간격과 여섯 줄 전체의 균일성을 함께 확인한 뒤 평균 간격으로 복구한다. 임의로 간격 허용치를 넓히지 않는다.
6. 확대 재분석 범위: 이미지 TAB 외에 네이티브 텍스트 PDF의 미확정 리듬, 기본 크기에서 TAB을 못 찾은 페이지도 확대한다. 원본 검출이 완전히 비어 있을 때만 확대 결과의 좌표계를 그대로 채택한다. 부분 검출은 기존의 마디·현·열 대응과 기존 확정 음 보존 검사를 유지한다.

## 결과

| 항목 | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| 정확한 운지·뮤트 / 1,014개 | 769 | 904 |
| 잘못 확정한 입력 | 49 | 0 |
| 원본 운지·뮤트 미입력 | 245 | 110 |
| 감지한 마디 / 104마디 | 96 | 104 |
| 전체 리듬 일치 / 104마디 | 78 | 100 |
| 운지·리듬 모두 일치 / 104마디 | 30 | 53 |
| 실제 음표 열의 음가 불일치 | 25 | 4 |

미입력은 틀린 숫자로 바꿔 채우지 않는다. 잡음 조건의 네 마디에는 여전히 음가 오류가 있으며 리듬 검토 상태로 남는다. `0` 오입력은 이 26개 조건의 결과이고 범용 오인식률 0%를 뜻하지 않는다.

확대 효과를 따로 측정한 6개 조건(총 234개 운지·뮤트)에서는 확대를 끈 경우 정확한 입력 178개, 켠 경우 196개였다. 두 경우 모두 잘못 확정한 입력 0개였다. 확대는 PDF/원본 픽셀에서 근거를 다시 읽는 방식이며 원본에서 소실된 획을 생성하지 않는다.

## 기존 악보 회귀 확인

로컬에 있던 네 PDF, 총 11페이지 / 229마디를 수정 전 엔진 스냅샷과 최종 엔진으로 각각 다시 분석했다. 스냅샷 실행은 Worker의 geometry 요청까지 이전 소스로 교체했는지 확인한다.

| 파일 | 마디 | 입력된 운지·뮤트 전→후 | 검토 마디 전→후 |
| --- | ---: | ---: | ---: |
| A Little Further | 40 | 467→467 | 21→21 |
| Flower Dance | 63 | 845→846 | 37→36 |
| 모든 날 모든 순간 | 57 | 992→992 | 0→0 |
| 여수밤바다 | 69 | 1,366→1,366 | 0→0 |

입력 개수는 전곡 정확도가 아니다. A Little Further의 독립 작곡 원본 508개와의 대조는 정답 467개, 오입력 0개, 전 40마디 리듬 일치를 유지했다. Flower Dance의 기존 수기 정답 10마디/151개는 정답 146개, 오입력 0개, 10마디 리듬 일치를 유지했다. 모든 날 모든 순간의 수기 정답 9마디도 일치했다.

Flower Dance의 추가 변화는 25·28마디다. 원본 2페이지를 별도 렌더링해 직접 확인했다. 25마디의 `8 8 16 16 16 16 8 8 4`, 28마디의 16분음표 16개가 복구됐고, 28마디 여덟 번째 음의 1번 줄 2프렛이 추가로 읽혔다. 나머지 미입력은 남는다.

전체 단위 테스트 1,718개 통과, 최종 빌드와 배포 미디어 검사 통과. 기존 청크 크기/혼합 import 등의 빌드 경고는 남는다. 실제 휴대폰 성능은 이번에 측정하지 않았다.

## 오선보 → TAB의 기본 운지

개발용 OMR 실험 화면에서 기보 옥타브를 명시적으로 선택하면 공유 `assignTab` 로직으로 개방현·1~4프렛과 작은 손 이동을 우선하는 운지를 제안한다. 사용자가 각 운지를 바꿀 수 있으며 음역 밖 음은 임의 이조하지 않고 미배치로 남긴다. 음표 인식 결과는 계속 미검토 상태다.

기존 로컬 OMR 모델과 네 음짜리 원본 PDF를 실제로 실행해 도·레·미·파 → `2:1, 2:3, 1:0, 1:1`, 수동 변경, 옥타브 변경에 따른 재배치, 기존 편집기 열기를 확인했다. 외부 요청과 브라우저 오류는 없었다. 이 시험 화면의 기존 단일 오선보·한 페이지·제한된 기호 범위는 그대로다. 일반 오선보 PDF 전체를 지원하는 정식 기능이나 모바일 PDF 메뉴 추가를 완료한 것은 아니다.

## 재현

필요 환경: 프로젝트 Node 의존성, Python의 reportlab/Pillow, Poppler `pdftoppm`, Playwright와 Chrome. 개발 서버는 기본 `http://127.0.0.1:5174`, 변경 시 `PDF_TAB_APP_ORIGIN`을 지정한다.

```powershell
# PYTHON 실행 경로는 현재 설치 환경에 맞게 지정한다.
python scripts/create-pdf-tab-corpus.py
$env:PLAYWRIGHT_MODULE='file:///.../playwright/index.mjs'
node scripts/verify-pdf-tab-corpus.mjs after
node scripts/report-pdf-tab-corpus.mjs
node --test tests/pdf-tab-robustness.test.mjs tests/omr-standard-fingering.test.mjs
npm test
npm run build
```

`tests/fixtures/pdf-tab-corpus-baseline.json`은 수정 전 측정치와 수정 후 최소 유지 기준을 보관한다. 보고 스크립트는 잘못 확정한 운지, 정답 수 감소, 리듬 회귀, 마디 누락, 브라우저 오류를 만나면 실패한다. 정답 기준을 인식 결과로 덮어쓰지 않는다.

확대를 끈 비교는 `PDF_TAB_DISABLE_ZOOM=1`로 별도 출력 이름을 지정해 실행한다. 기존 악보 재검사는 `verify-pdf-tab-existing-corpus.mjs`와 이전 수기 감사 스크립트를 사용하며, 개인 악보와 이전 엔진 스냅샷이 로컬에 있어야 한다. OMR UI 재검사는 선택 설치된 모델 및 기존 네 음 PDF가 있을 때 `verify-omr-standard-ui.mjs`로 실행한다.

생성 PDF·PNG·분석 JSON은 `artifacts/pdf-tab-corpus`에만 저장하고 Git·배포에서 제외한다. 생성기, 채점기, 오류 재현 테스트, 집계 기준만 소스로 관리한다.
