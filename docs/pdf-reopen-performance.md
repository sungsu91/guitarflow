# 저장된 PDF 다시 열기 개선

## 원인과 저장 확인

`pdfLibrary.js`의 IndexedDB `fretiva.pdf.library.v1`는 `scores`에 메타데이터·썸네일을, `files`에 `{id, pdfBlob}`을 저장한다. `getPdf()`는 저장된 Blob을 읽는다. 파일 경로나 object URL을 원본 대신 저장하지 않는다. object URL은 원본 PDF 내려받기에만 일시적으로 사용된다.

실제 브라우저에서 저장 후 새로고침한 9,249,597바이트 PDF가 `Blob`, `application/pdf`, `%PDF-` 헤더로 복원됨을 확인했다. 보관함에서 다시 열 때 시스템 파일 선택창 호출은 0회였다.

기존에는 PdfPage/PdfContinuous가 마운트될 때마다 새 PDF.js loading task를 만들고, 닫을 때 worker를 파괴했다. 렌더링 시작 시에도 기존 캔버스를 빈 캔버스로 교체했다. 연속 보기에서는 모든 페이지를 순회하여 크기를 먼저 읽었다. 저장 실패가 아니라 이 수명 관리·표시 순서가 반복 로딩의 원인이었다.

## 변경

- 저장된 썸네일 또는 같은 페이지의 최근 캔버스를 먼저 표시한다. 새로운 캔버스는 화면 밖에서 완성한 뒤 교체한다.
- 200ms 미만에는 로딩 문구가 없다. 더 오래 걸리면 기존 페이지 위에 작은 표시만 나타난다. 제목·하단 조작부는 유지한다.
- PDF.js 문서 캐시는 최근 2개, 비활성 5분 유지다. 사용 중인 문서는 먼저 폐기하지 않는다.
- 페이지 이미지 캐시는 최대 8개 / 32MiB이며 LRU로 정리한다. 표시 중인 캔버스와 worker 내부 메모리는 이 이미지 캐시 용량과 별도다.
- 키는 문서 id·원본 지문·페이지·표시 너비·배율·기기 픽셀 비율·자르기 영역이다. 변경한 페이지/배율만 새로 렌더링하며 기존 정확한 변형은 Undo에 재사용할 수 있다.
- 펜·텍스트·텍스트 회전·마디 매핑은 원본 페이지 좌표의 별도 오버레이다. 해당 오버레이만 바꾸며 PDF 이미지 캐시를 지우지 않는다. 새 PDF 페이지 회전 UI는 추가하지 않았다.
- 단일 보기: 현재 페이지 완료 후 유휴 시간에 다음/이전 페이지를 순차 준비한다.
- 연속 보기: 현재 페이지와 유휴 시간의 이웃 페이지만 해석/렌더링한다. 전체 페이지를 처음부터 순회하지 않는다.
- 연속 보기 마지막 페이지가 화면보다 짧아 위에 이전 페이지 일부가 보일 때 마지막 페이지 선택을 잘못 바꾸던 문제도 수정했다.
- 세션을 완전히 종료하거나 새로고침하면 메모리 캐시는 사라진다. 이때도 IndexedDB 썸네일을 사용한다. 원본 저장 형식·백업 형식은 변경하지 않았다.

## 390×844 실제 Chrome 터치 에뮬레이션

3페이지 / 약 9.25MB PDF, 개발 서버, 별도 브라우저 프로필에서 측정했다. 완료 시간은 클릭부터 렌더 완료 상태까지이며 실기기 보장 수치가 아니다.

| 구분 | 최초 화면 표시 | 렌더 준비 완료 | 로딩 표시 |
| --- | ---: | ---: | --- |
| 첫 진입 | 썸네일 16.5ms | 2,316ms | 200ms 이후 작은 표시 |
| 두 번째 진입 | 캐시 15.3ms | 37.9ms | 없음 |
| 마지막 2페이지 재진입 | 캐시 11.3ms | 38.4ms | 없음 |

두 번째 진입에서 문서 생성 수는 1개 그대로, 실제 PDF 렌더 수도 2회 그대로였다(첫 페이지 + 다음 페이지 사전 준비). 다음 페이지 이동도 캐시를 사용했다.

문서 준비를 의도적으로 600ms 지연한 검사에서는 썸네일이 19.3ms에 나타났고, 작은 로딩 표시는 234ms에 나타났다. 큰 빈 로딩 화면은 나타나지 않았다.

24페이지 PDF의 마지막 페이지를 연속 보기로 열었을 때 요청/렌더링한 것은 24·23페이지 두 개뿐이었다. 다시 열어도 worker 생성 및 실제 렌더 횟수는 늘지 않았다.
